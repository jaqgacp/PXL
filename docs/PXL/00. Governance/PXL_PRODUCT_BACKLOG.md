## Backlog Rules

- Official defects and release blockers belong only in `PXL_END_TO_END_AUDIT_FINDINGS.md`.
- This file refers to defects by ID and never duplicates their full evidence or remediation.
- Posting changes must first be defined in `docs/PXL/02. Accounting Core/PXL_ACCOUNTING_RULES_MATRIX.md`.
- Transaction field/source changes must remain synchronized with `docs/PXL/04. Transaction Framework/PXL_TRANSACTION_MATRIX.md` and `docs/PXL/04. Transaction Framework/PXL_TRANSACTION_FIELD_SOURCE_MATRIX.md`.
- Nothing here is authorized merely because it is listed. Work must be selected in `AI/AI_STATE.md` or explicitly approved.
- The Accounting Core Ready gate remains active; broad UX/report/dashboard rollout waits behind its security, accounting, tax, CAS, source, and regression prerequisites.
- **Every compliance capability is measured against one pipeline** (owner decision, 2026-08-04). A compliance item is scoped, estimated and reported as its position along:

  > Posted Transactions → Tax Engine → Tax Ledger → Reconciliation → Working Paper → Filing Artifact → Export → Filed Record

  Each stage is a **consumer** of the one before it. No feature may bypass a stage, and no feature may introduce a second engine at any stage — no filing-specific calculator, no export-side recomputation, no browser aggregation. A future form registers itself as configuration in `ref_filing_artifact` and consumes the existing posting, tax-ledger and reconciliation framework. Form-specific rules belong in metadata, configuration and effective-dated masters, **not in hardcoded branches**. A **Filing Artifact** is what PXL generates; a **Filed Record** is the accountant's declaration that it was submitted. PXL never infers BIR acceptance and will not do so without a deliberate e-submission capability.
- **The Filing Artifact is the system of record for compliance outputs** (owner decision, 2026-08-04). Any UI, export, snapshot, API or integration must **consume the Filing Artifact**, never rebuild a compliance report from transactions, from the tax ledger, or in the browser. An item that proposes to read source tables or views for a compliance output is not scoped as written — it is scoped as a migration onto the artifact layer. **As of 2026-08-05 every current-product compliance surface consumes the Filing Artifact**, asserted by test `129` and `tests/compliance_architecture.test.ts`. The FWT/1601FQ prototype screens are an excluded future extension and do not participate in current-product conformity or readiness.
- **Review Stage and Filing Stage are different stages of the one pipeline** (settled 2026-08-05 while delivering item 8e ii, which is the case that forced it). The rule above binds the **Filing Stage**, not every screen that mentions tax. The test is: **if a figure would be keyed onto a BIR form, it comes from the Filing Artifact; if it exists to find the document with the missing tax code before anything is generated, it reads source data by design.**
  - **Review Stage** — the SLS and SLP registers, RELIEF, the Output/Input VAT and Percentage Tax reviews, and the compliance dashboards. These read posted transactions and `vw_*` review views deliberately. Their job is data quality *before* generation, and they are correct to show a live figure that a settled artifact does not. They are the pipeline's first stage — *Posted Transactions* — not a bypass of it.
  - **Filing Stage** — working paper, artifact, export, filed record. Bound to the artifact absolutely; `FILING_PAGES` in `tests/compliance_architecture.test.ts` is the enumerated list and the guard fails if one of them reads a source view.
  - **Why it needed stating:** `vw_ewt_summary_ap` deliberately drops reversal pairs, which is right for review ("what is withheld now?") and was wrong for the QAP alphalist, which must tie to the 1601EQ. Same data, two correct answers, different stages. Without the distinction a future session would either "fix" a review screen to match a return or, worse, build a return from a review screen.
- **Product scope is Philippine SME accounting and compliance** (owner ruling, 2026-08-04). The following are **future product extensions only** — not current product scope, not pilot scope, and **not production-readiness requirements**. They must never be listed here or anywhere else as production blockers, pending architecture gaps or required delivery items: **Final Withholding Tax (1601FQ / 2306)**, **Payroll**, **Form 2316**, **Quarterly and Annual Income Tax**, **MCIT / RCIT**, **NOLCO**, **OSD**, **Fringe Benefits Tax**, **Transfer Pricing**, **Consolidation Tax**, and **specialized-industry tax features**. An item covering any of them is recorded with the 🔮 marker and carries no readiness weight. **After the current compliance work, the ranked future priorities are Banking & Treasury, then Fixed Assets** — both ahead of every excluded capability, and neither authorised to start.
- **Exactly one authoritative implementation per pipeline stage, per compliance area** (owner decision, 2026-08-04). **Parallel implementations are not allowed.** Where a stage needs several faces they must be delegations that compute nothing of their own. A backlog item that would create a second implementation of any stage is not scoped — it is rewritten as a migration onto the existing one. Two corollaries, both load-bearing: **(a) replacement is ordered, never reversed** — migrate consumers, verify no dependency remains, then retire the legacy objects, and never drop one before its replacement is reachable; a superseded store is retired rather than populated. **(b) No orphans** — an object no governed consumer reaches is either integrated into the pipeline or retired when its item becomes active; dead code is not kept indefinitely. The full rule is in `docs/PXL/02. Accounting Core/PXL_ACCOUNTING_RULES_MATRIX.md`.
